این فایل تنها منبع canonical و self-contained قوانین نسخهٔ `current canonical rules` است و به JSON، rule pack یا فایل قانون خارجی وابسته نیست. منابع مرجع پروژه را فقط در صورت ارتباط با scope و به‌ترتیب نیاز بخوان: `README.md`، `AGENTS.md`، plan فعال، history مرتبط، configuration و `SKILL.md`های مرتبط. هیچ منبع خارج از scope یا دارای secret خام را load نکن؛ freshness cache و graphify را پیش از اتکا validate کن.

[must] api-output-class-contract: `ErroExtion` کلاس canonical خروجی API و تنها abstraction مجاز برای envelope استاندارد است؛ کلاس‌های موازی مانند `ApiResponse`، `ApiResult`، `BaseResponse`، `ResponseDto` یا wrapperهای هم‌معنا نساز. این کلاس باید حداقل فیلدهای `isSuccess`، `data`، `errorMessage` و `context` را با serialization پایدار ارائه کند. `data` باید type-safe و متناسب با use-case باشد: در پاسخ تک‌موردی یک DTO، در پاسخ list همیشه آرایهٔ همگن، و در نتیجهٔ خالی `[]` باشد. `ErroExtion` نباید Entity، مدل دیتابیس یا persistence model را مستقیماً expose کند. مسیر صحیح پاسخ چنین است: `Domain/Application → Output DTO → Mapping → ErroExtion<T> → API serialization`. نمونهٔ پاسخ موفق: `{ "isSuccess": true, "data": { "id": 1, "name": "..." }, "errorMessage": "", "context": {} }`
نمونهٔ list صفحه‌بندی‌شده: `{ "isSuccess": true, "data": [], "errorMessage": "", "context": {}, "totalCount": 0, "pageIndex": 0, "pageSize": 20, "hasNext": false, "hasPrevious": false }`

[must] plan-authoring-activate-on-command: Detect macro, micro, execute, or loop phase and announce the phase, invoked skills, and active skill.
[must] plan-authoring-wave-based-macro: In macro mode, complete the orchestrator and first wave while representing later waves as stubs; expand the next wave only after the current wave completes.
[must] plan-authoring-two-phase-model: Plans have a macro whole-project map and a micro implementation plan using writing-plans; every Part needs a micro plan before execution.
[must] plan-authoring-plan-versioning: The orchestrator must contain planVersion, promptSpecVersion, and updatedAt; increment planVersion when a Part contract or structure changes.
[must] plan-authoring-api-compatibility: API Parts are additive, preserve aliases and migration paths for renames, keep the envelope stable, and include legacy tests.
[must] plan-authoring-migration-rollback: Migration Parts must document rollback or irreversibility, application rollback, and idempotent seeds.
[must] plan-authoring-wave-smoke: Before completing a wave, smoke health for every touched host and at least one E2E path per applicable surface, with evidence.
[must] plan-authoring-loop-orchestration: In a local loop, each tick executes one ready Part or the next wave; stop when the orchestrator completes and do not use cloud loops.
[must] plan-authoring-finishing-branch: After wave/domain verification, report readiness and finishing-branch options only; commit, PR, merge, rebase, branch cleanup, and release require explicit user authorization under `git-safety`.
[should] plan-authoring-verify-gates: If a project verify manifest exists, run its gates before completing a wave/domain.
[must] plan-authoring-blocker-precedence: Resolve blockers from the repository; after execute starts continue uninterrupted, stopping only for secrets, a dead service, or an explicit user instruction.
[may] plan-authoring-optional-dag-visual: A Mermaid DAG may improve readability but never replaces the machine registry.
[must] plan-authoring-context-first: Before a Plan, read only resources relevant to scope and profile; business models, mockups, and competitor references are required only for product/UI/commercial decisions and are not loaded for independent technical work.
[must] plan-authoring-orchestrator: The orchestrator contains only the header, goal, architecture, tech stack, domain registry, waves, DAG, and global status; micro details are forbidden there.
[must] plan-authoring-no-placeholders: Ready and executable Parts/micro plans may not contain TBD, undefined references, or placeholders; TODO is allowed only for blockers or deferred work under todo-traceability.
[should] plan-authoring-dedicated-worktree: Propose or create an isolated worktree for critical, multi-branch, or high-risk changes; continue in the current worktree for quick/standard unless isolation has clear value. Never move or delete existing user changes when creating one.
[must] plan-authoring-dry-yagni: Keep one source of truth, avoid duplicated logic, and do not add unnecessary abstractions or future features in macro or micro plans.
[must] plan-authoring-plan-reviewer: Before a Part becomes ready, a reviewer must check completeness, specification alignment, and buildability.
[must] plan-authoring-implementation-session: Before execute, record only the required handoff and, when `plan-authoring-dedicated-worktree` activates, the isolated path; then continue relevant Part/Result/history without unnecessary questions.
[must] plan-authoring-three-surfaces: When applicable, every feature covers backend API, admin panel, and user/public surfaces; lists use the complete feature matrix.
[must] plan-authoring-end-to-end-layers: Cover all applicable domain, application, API, migration, UI, i18n, theme, envelope, test, and verification layers end to end.
[must] plan-authoring-skills-workflow: Adapt workflow by profile: quick=`execute → verify`; standard=`plan → execute → verify → review`; critical=`macro → review → micro → isolation-if-needed → execute → verify/smoke → Judge → finishing-options`. Do not execute or report irrelevant stages.
[must] plan-authoring-delivery-priority: Use macro/micro only when complexity and dependencies require them; business models and mockups precede work only when their triggers are relevant. Do not manufacture Plans for small tasks.
[must] plan-authoring-hierarchy: Use the hierarchy orchestrator → domain → Part → command → microStep and keep detail at the correct level.
[must] plan-authoring-scope-check: Put independent subsystems in independent domains; each domain must be independently testable and deliverable.
[must] plan-authoring-structure-before-tasks: Define responsibility boundaries, interfaces, and affected layers before tasks; group co-changing files in a coherent Part.
[must] plan-authoring-json-prompt-format: Macro output must be a UTF-8 no-BOM JSON Prompt with metadata, parts, results, a machine registry, and valid statuses.
[must] plan-authoring-bite-sized-steps: Each micro step is a 2–5 minute action with a checkbox, command, expected output, and verification; use TDD when applicable.
[must] plan-authoring-status-prerequisites: Every domain and Part has status and prerequisites; a Part without microPlanStatus=ready cannot enter implementation.
[must] plan-authoring-parallel-multitask: Use DAG and waves for independent parallel Parts and preserve dependency order across layers.
[must] plan-authoring-command-linking: Every command and micro step has dependsOn, linkedCommands, and a reference to its Part or previous step; isolated commands are forbidden.
[must] plan-authoring-customer-and-value-add: Record customer needs, competitive references, product standards, and future value-adds separately and clearly.
[must] omp-custom-agent-model-routing: In OMP, every custom agent must have an explicit, resolvable model alias; `customer` must use `@customer`, and `modelRoles.customer` must map to a valid model with a corresponding fallback in `retry.fallbackChains.customer`. Missing this mapping is a configuration defect, and assigning the agent to a general role such as `@vision` is not an equivalent. Customer activation remains opt-in and is allowed only with `customer on` or an equivalent direct instruction.
[must] omp-customer-advisory-block-threshold: After activation, Customer is advisory and a disagreement or low/medium finding must not block the workflow. Only a demonstrated high/critical defect with scope-relevant evidence may request a Judge block; a clarification blocks only when acceptance cannot be evaluated without a required user decision. New-scope requests and in-scope improvements must be reported and routed, not used to stop task execution by default.
[must] autonomous-agent-decision-policy: Agent Main must make and execute technical decisions inside scope using repository evidence, official documentation, tests, and bounded inference. Advisory disagreement, info/low/medium findings, in-scope improvements, unavailable optional tooling, and new-scope requests must not create a block or user question by themselves; record and route them. Ask the user only when the issue is blocking and non-inferable, both technical paths cannot resolve it, the cost of error is material, and the decision is genuinely user-owned. Only a valid high/critical finding with evidence and a precise resume condition may block; missing seats or subagents are reported as degraded and never fabricated.
[must] block-to-decision-routing: A technical block is not the end of the workflow or an automatic project stop. Agent Main must convert it into a decision packet containing the issue, evidence, real options, trade-offs, recommended option, owner, action, verifyMethod, and residual risk, then choose and execute the best safe in-scope option. The active state is `decision-required` or `ACTION REQUIRED`. Only a hard safety or authorization stop may halt execution: secret containment, destructive/production work without authorization, missing required access or credentials, a genuinely user-owned legal/business decision, or no safe fallback. Even then record safe interim work and an exact resume condition; bare blockers are forbidden.
[must] plan-authoring-mockup-fidelity: Every page must link to its reference mockup; visual changes require an explicit override.
[must] plan-authoring-bilingual-density: Macro plans must include fa and en details, measurable acceptance, and sufficient domain coverage; code and command language may be English.
[must] plan-authoring-self-review: Before a macro becomes ready, self-review customer coverage, placeholders, names/types/API, three surfaces, and an acyclic DAG, then fix gaps inline.
[must] plan-authoring-frequent-commits: Default commits are forbidden; commit at complete boundaries after gates only when the user explicitly requests it.
[must] plan-authoring-micro-plan-template: Every micro plan includes a Task header, Files, and verifiable steps with action, expected result, and verification; include commit only with explicit user authorization.
[must] plan-authoring-single-source: Keep one source of truth for the macro and micro representation of each Part; remove contradictory duplication.
[should] plan-authoring-domain-catalog: For CMS/Telecom projects, consider auth, profile, settings, i18n, theme, public, panels, integrations, observability, testing, and verification domains.
[should] ide-vscode-per-project-editor-chrome-color: Configure each workspace's title bar and status bar only in that workspace's `.vscode/settings.json`; do not change global User Settings, syntax themes, or unrelated settings.
[must] package-manager-pnpm: Use `pnpm` instead of `npm` in all projects; replace npm-based install, run, and dependency-management commands (`npm install`, `npm run`, `npm ci`, etc.) with their pnpm equivalents (`pnpm install`, `pnpm run`, `pnpm fetch` / `pnpm install --frozen-lockfile`, etc.) and keep pnpm as the default package manager.
[must] asset-file-separation-html-css: In projects that support placing HTML and CSS in separate files (such as Angular), separate content from structure and styling: place HTML in a template file and CSS in a separate style file, and avoid inline or directly embedded HTML/CSS in component/logic files, unless justified by a documented technical reason (such as Tailwind with a stated reason).

[must] state-transition-prerequisite-child-traceability: A full status graph is required only for Plans, loops, and standard/critical tasks; quick uses `status | evidence | nextAction`. The full contract is `id | status | allowedTransitions | prerequisites | children | dependsOn | owner | priority | blocker | evidence | completionCriteria`. Record only changed transitions with UTC timestamp and reason; do not repeat unchanged snapshots. Cycles, orphans, unknown dependencies, or completing a parent with unfinished children are blockers. The 7Expert relevance mask links to the graph, but unrelated domains do not get separate nodes.

[must] todo-format-variants-and-readability: The following formats are valid and standard for writing `TODO` in code, configuration, migrations, tests, documentation, translations, and metadata: simple form such as `// TODO: fix this bug`; owner form such as `// TODO [owner]: add validation`; date or task form such as `// TODO: (1405-06-27) optimize the database query` and `// TODO [TASK-142]: complete migration`; owner and priority form such as `// TODO [Backend, P1]: add idempotency to the endpoint`; and canonical form for dependent or blocked work such as `// TODO(Backend, P1): Complete response mapping; blocked-by: canonical DTO contract; done-when: contract tests pass for legacy and new consumers.`. `TODO:` must use Latin letters, appear at the nearest relevant location, use valid comment syntax for the language, and state the remaining action. Owner, date, task ID, and priority are optional for simple work, but owner and completion criteria are mandatory for multi-part, blocked, security-sensitive, or dependency-bound work. The preferred date format is `YYYY-MM-DD`; a Persian-calendar date is allowed only with an explicit `JYYYY-MM-DD` marker. A task ID must reference a valid tracker or Plan, and the owner may be a person, role, team, or domain; secrets, credentials, PII, and raw logs are forbidden. Vague entries such as `TODO: later` or `TODO: fix` without explanation are forbidden. For TODOs with a blocker, dependency, or critical priority, `blocked-by` and `done-when` are mandatory in canonical form. TODO never replaces implementable in-scope implementation, testing, or verification; every TODO must remain traceable under todo-traceability in Plan/Part/Result or history and receive `resolved`, `accepted-risk`, or `blocked` status before completion. Out-of-scope TODOs must be labeled `out-of-scope`.
